# Переезд с Remnawave на XLADA с сохранением пользователей

Короткая инструкция. Общее описание переезда — в `MIGRATE_FROM_REMNA.MD`
в корне рабочей копии.

## Какой файл использовать

`deploy/docker-compose.migrate-from-remnawave.yml`

Он отличается от обычного `deploy/docker-compose.yml` только тем, что
сохраняет имена и том вашей существующей установки. Обычный compose
разворачивает новую установку с нуля и создал бы **пустую** базу.

## Две ловушки

**Том базы.** В старой установке данные лежат в томе `remnawave-db-data`.
Обычный compose XLADA использует `xpanel-db-data` — это другой том, и в
нём ваших пользователей нет. Файл для переезда указывает на старый том.

**Версия PostgreSQL.** Каталог данных несовместим между мажорными
версиями. База создана `postgres:17.6` — файл для переезда использует ту
же версию и монтирует том туда же, где он был
(`/var/lib/postgresql/data`). Образ `postgres:18` использует другой путь
и откажется читать данные 17.

На 18 можно перейти позже, отдельным шагом: сделать дамп, поднять чистую
базу 18 и восстановить дамп в неё.

## Что менять в `.env`

Ничего не удалять. Проверить и оставить как есть:

| Переменная | Почему нельзя менять |
|---|---|
| `APP_SECRET` | От него зависят хеши паролей и зашифрованные секреты. Смена = никто не войдёт |
| `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB` | Должны совпадать с тем, что уже создано в базе |
| `DATABASE_URL` | Хост в нём — `remnawave-db`. Имена сервисов сохранены, поэтому адрес остаётся верным |
| `PANEL_DOMAIN`, `FRONT_END_DOMAIN`, `SUB_PUBLIC_DOMAIN` | Адреса, по которым работает панель |

Добавить (обе необязательные, есть значения по умолчанию):

```ini
# Тег образа XLADA, который подтягивается
XLADA_VERSION=1.1.3

# Сколько дней хранить журнал действий администраторов
AUDIT_LOG_RETENTION_DAYS=30
```

Если будете поднимать страницу подписки — отдельный файл
`deploy/.env.subpage` со своим `REMNAWAVE_API_TOKEN`.

## Порядок

```bash
# 1. Резервная копия базы и файла окружения
docker exec remnawave-db pg_dump -U "$POSTGRES_USER" "$POSTGRES_DB" > ~/remnawave-backup-$(date +%F).sql
cp deploy/.env ~/remnawave-env-backup

# 2. Остановить старый стек. ВНИМАНИЕ: без флага -v!
cd deploy && docker compose down

# 3. Запустить XLADA на той же базе
docker compose -f docker-compose.migrate-from-remnawave.yml up -d

# 4. Смотреть, как применились миграции
docker logs -f remnawave
```

## Чего делать нельзя

- **`docker compose down -v`** — флаг `-v` удаляет тома вместе с базой.
  Это единственная команда, которая действительно уничтожает
  пользователей.
- **Менять `APP_SECRET`** — пароли перестанут подходить, восстановить
  можно только сбросом через базу.
- **Поднимать версию PostgreSQL** на существующем томе.
- **Переименовывать тома и сервисы** — тогда compose создаст новые
  пустые, а старые останутся висеть рядом.

## Проверка после переезда

```bash
# панель отвечает
curl -s -o /dev/null -w '%{http_code}\n' https://panel.example.com/api/auth/status

# база видит пользователей
docker exec remnawave-db psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -tAc "SELECT count(*) FROM users;"

# миграции применились без ошибок
docker logs remnawave 2>&1 | grep -i "migrat" | tail -5
```

Число пользователей до и после переезда должно совпадать.

## Что появится после переезда

Миграции XLADA только аддитивные: они добавляют журнал действий
администраторов и поля для второго фактора, ничего не удаляя. Поэтому
переезд обратим: достаточно вернуть прежний образ панели.
